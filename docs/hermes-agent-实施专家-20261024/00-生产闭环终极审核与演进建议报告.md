## 一、结论摘要

### 1.1 审核结论

| 场景 | 结论 | 说明 |
| --- | --- | --- |
| 个人本地自用 | **有条件通过** | P0 项（运行时重建、brotli 锁内漏洞、uv 工具链、上游同步）闭环前，不建议把当前 venv 当作可信基线 |
| 小团队内部使用 | **有条件通过** | 需补齐 SBOM、审计留存、公开站点安全头、类型门禁 |

### 5.2 运行时基线（2026-10-24 复核更正）

> **更正说明**：初次采集使用 `pip list` 时，Hermes venv 内没有 pip，命令落到 `/opt/miniconda3/bin/pip`，因此“194 包 / 226 条 OSV”实际属于 conda base 环境，与 Hermes 运行时无关。复核改用 `importlib.metadata` 枚举 venv，结果如下。

| 项 | 复核结果 |
| --- | --- |
| venv 发行包 | **97**（P0 同步后 **109**） |
| 与 `uv.lock` 版本偏差 | **0** |
| OSV 记录 | **0 条 / 0 包** |
| 关键包 | cryptography 50.0.2、PyJWT 2.15.1、aiohttp 3.14.5、certifi 2026.10.19、urllib3 2.8.0、requests 2.33.0、mcp 2.2.0 |
| brotlicffi | 未安装（`messaging` extra 未启用）；锁内已升至 1.2.1.0 |

**初次发现的 6 个“漂移”包**中，`aiohappyeyeballs`、`multidict`、`propcache` 已回退到锁版本；`botocore`、`s3transfer`、`tabulate` 属历史 extras 残留，P0 同步时按 `[all] + dev` 基线移除。最终 109 包与锁文件 0 偏差。

**真正的风险不是漂移，而是测量链**：venv 无 pip，`hermes doctor` 却建议 `pip install -e '.[all]'`；该命令会落到 conda pip，污染 base 环境。这已列为 P1（见 M3）。

**保留的真实失败**：复核后 `tests/tools/test_mcp_oauth_manager.py` 仍有 2 例失败，定位为 `mcp 2.2.0` 的 `_httpx_utils` 与测试 mock 的 `SimpleNamespace` 契约不一致，属于真实兼容性问题，保留 triage；它不是环境漂移。

**教训**：环境审计必须先打印 `sys.executable` 与 `pip --version`；优先用 `importlib.metadata` 或 `uv pip list --python <venv>`，不要信任 PATH 上的 `pip`。

### 5.3 执行边界

[SECURITY.md](../../SECURITY.md) 的表述非常清醒：**唯一的对抗性 LLM 边界是操作系统级隔离**；审批门、输出脱敏、模式扫描、工具白名单都只是启发式。

| 项 | 现状 | 风险 |
| --- | --- | --- |
| 默认终端后端 | `terminal.backend = "local"` | Agent 直接以当前 OS 用户权限执行 shell |
| 审批模式 | `approvals.mode = "smart"` | 由分类器判断危险命令，仍是进程内启发式 |
| 无人值守 | `cron_mode/single_query_mode/unattended_mode = "deny"` | 默认失败关闭，设计正确 |
| 沙箱可选 | Docker / SSH / Singularity / Modal / Daytona / Vercel | 能力齐全，但本地默认未启用 |
| 建议 | 对网页、邮件、MCP 等不可信输入，使用 Docker 或远端后端；高风险场景使用整进程包裹 | 本地自用也应把“不可信内容”与“宿主权限”分开 |

### 5.6 CI 与供应链门禁

**强项**：

- 37 个 workflow，覆盖 tests、lint、OS 矩阵、Docker、Pages、install-e2e、lockfile、OSV、supply-chain。
- GitHub Actions 全部按 SHA 固定；Docker 基础镜像按 digest 固定。
- Python 精确 `==` 锁定；npm 有 14 天发布年龄门。
- supply-chain 扫描器只保留高信号规则（`.pth`、可疑安装脚本等），避免告警疲劳。

**缺口**：

1. 本地 `uv` 版本未纳入门禁；CI 固定 0.9.28，但本机 0.9.7。
2. 本地 `npm audit` 默认 registry 不可用。
3. `hermes doctor` 的安全公告库滞后：本次它显示“无活跃安全公告”，但 2 天前发布的 brotli critical 已在 OSV。
4. `ty` 在 CI 中是 advisory diff，不阻塞。
5. 无发布级 SBOM/签名/来源证明。

2. API Server 默认关闭；确需开启时设置强 `API_SERVER_KEY`，并置于带认证的反向代理后。
3. 不可信内容（网页、邮件、MCP 响应）使用 Docker/远端终端后端；本机 local 后端只处理可信仓库。
4. 审批保持 `mode=smart`，并追加 deny globs：`rm -rf*`、`git push --force*`、`curl*|*sh`、`chmod 777*`、`~/.ssh/*`。
5. 关闭不用的消息平台与工具，减少 token 与攻击面（`hermes tools`）。
6. 记忆优先内置 provider；如无必要，关闭云记忆与外部搜索，保证数据主权。
7. 备份 `~/.hermes`（`state.db`、`config.yaml`、`skills/`、`memories/`），并每季度做一次恢复演练。
8. `.env` 权限 `0600`；密钥只放 `.env`，不放 `config.yaml`；无效 key（当前 GLM）立即轮换或删除。
9. 每周跑一次 `hermes doctor` + OSV 扫描；但**不要只信 doctor**，本次它未发现 2 天前的 brotli critical。
10. 工具版本统一：`uv >= 0.9.28`、`rg 15.1.0`、Python 3.11.x、Node 22.22/24.11；把版本检查写进启动脚本。
