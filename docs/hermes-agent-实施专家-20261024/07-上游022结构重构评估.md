## 0. 结论速览（书面合并决策）

**推荐：方案 (a) —— 保持 0.21.3 基线 + 安全类补丁定点 backport；不做整树 rebase，不追上游常规修复。同时把「整树切换」升级为 0.23.0 发布后的正式评估项（方案 c 的收敛版），触发条件见 §7.3。**

理由三行：

1. **上游是超高速增长期，不是重构沉淀期**——v0.22.0 官方口径自 v0.21.0 以来 24,200 commits / 6,080 PRs；main 一周又 +2,971 commits。此时整树切换 = 登上永不停歇的跑步机，且 0.23.0 已在路上。
2. **实测冲突面可控但无紧迫收益**——我方 54 commits 触及 184 文件，与上游变化集交集 81 文件；其中约 6 成为机械文件（workflows/lockfile/图标），真正需人工合并约 20 文件。但本分支价值在 ops/品牌/安全/docs 层，引擎层滞后没有造成任何已知故障。
3. **不切换的成本在累积**——平台层插件化（gateway→plugins/platforms）、compat 导入层删除、memory provider 迁 catalog 都是「回不去」的结构重构；拖过 2-3 个 minor 版本后，切换成本将指数上升。故设 0.23.0 为下一次正式评估点，而非无限缓议。

## 7. 合并策略决策

### 7.1 三选一评估

| 方案 | 评估 |
|---|---|
| **(a) 保持 0.21.3 基线 + 安全补丁定点 backport** | ✅ **推荐（当期）**。本分支已自发形成该模式：deps 批次 A-F、dashboard-auth backport、P0-5 头部均是先例且运转良好；冲突面为零（单文件、独立上下文）；维护成本可预测 |
| (b) 按模块 cherry-pick 上游关键修复 | ⚠️ 仅限「独立文件级修复」。在 11,611 文件漂移的背景下，凡涉及被重构模块（gateway 平台层、memory、electron、doctor）的 cherry-pick 都会因上下文不匹配而变成重写；批量 cherry-pick 实际等于半次整树切换，却承担双倍复杂度。**不作为常规手段** |
| (c) 等待上游 0.22.x LTS 后整树切换 | ⚠️ **「LTS」前提不成立**：上游无 LTS 机制，v0.22.5 只是 patch rollup，main 已领先 2,971 commits（7 天），0.23.0 在途。无限等待 = 成本单调上涨（§4 的结构性漂移每 minor 加深一次）。**改造为「0.23.0 发布后做整树切换正式评估」**，见触发条件 |
